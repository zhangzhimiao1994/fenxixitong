# 独立评审规范（基于真实运行结果）

## 参数

- `<REPO>`：仓库根目录，下文所有 skill 路径都在 `<REPO>` 下。
- `<RUN_DIR>`：本轮运行结果目录，默认 `evals/runs/<round>/`。
- `<BASE_DIR>`：对照组目录，默认 `evals/baselines/`（本轮补跑的新题在 `<RUN_DIR>` 里）。
- `<JUDGE_ID>`：评审编号，A / B / C。

你是**独立评审**，只读、只打分，不修改仓库文件，也不做版本控制操作。

## 评审对象

- 主 skill：`<REPO>/skills/cross-system-hub/SKILL.md`
- 它的参考文件：`skills/cross-system-hub/references/translation-and-plan.md`；它调用的维度入口（维度表里列出的入口 skill）
- 结构维度只评主 skill。路由里的缺陷如果导致了运行问题，在 d8 里扣分，并写进 fix_proposals

## 运行结果

- `<RUN_DIR>/run_<ID>.md`：装了 skill 的 agent 真实执行的结果，包含 执行记录 和 REPLY
- `<BASE_DIR>/base_<ID>.md`：不带 skill 的对照组回复
- 用户原题：`<REPO>/skills/cross-system-hub/test-prompts.json` 里对应 id 的 prompt 和 expected

## Rubric（9 维，权重合计 99）

| # | 维度 | 权重 | 要点（1-10 分） |
|---|------|:---:|------|
| 1 | Frontmatter | 7 | description 写清"做什么 + 何时用 + 触发 + 不触发 → 去哪"，≤1024 字符，单行，合法 YAML |
| 2 | 工作流清晰度 | 12 | 步骤有序、可执行，输入输出明确；9 个维度的激活、排序、写法之间没有矛盾 |
| 3 | 失败模式编码 | 12 | "如果 X 失败 → Y"的显式分支、兜底 |
| 4 | 检查点 | 6 | 显性的 🔴 / 🛑 标记，写明停下来做什么 |
| 5 | 可执行具体性 | 17 | 具体参数、格式、示例；软化词（建议/可以考虑/根据情况/灵活/视情况）出现 ≥3 处扣 ≥3 分 |
| 6 | 资源整合 | 4 | 引用的 skill、文件、工具命令都存在、可达（在 <REPO> 下用 Glob 核实） |
| 7 | 整体架构 | 12 | 层次清晰、不冗余；6 维改 9 维后有没有残留的旧说法、互相打架的规则 |
| 8 | 实测表现 | 23 | 见下 |
| 9 | 反例黑名单 | 6 | 有"不要做"表，并且覆盖新维度带来的风险 |

**d8 实测表现**：逐条对比 `run_<ID>` 的 REPLY 和 `base_<ID>`，再对照 执行记录 检查 agent 是否按 skill 执行。看这几项：

- 是否完成用户意图
- 是否比对照组明显更好
- 安全处理是否正确
- 是否编造工具结果
- 篇幅和问题数是否合规
- 回复里有没有内部术语外露（如"体系分析""主要矛盾""维度"）
- 新维度的主次是否合理

执行记录 里记录的 skill 歧义和矛盾要认真对待，这是 skill 本身的问题。每条给 1-10 分，d8 取平均（全部测试题都要评，不得抽样；id 16 及以后的扩展题同样严格）。

**打分要严格**：任何可指出的具体缺陷，该维最高 8 分；9 分表示找不出能点名的缺陷。

## 产出

写 `<RUN_DIR>/judge_<JUDGE_ID>.json`：

```json
{"scores":{"d1":0,"d2":0,"d3":0,"d4":0,"d5":0,"d6":0,"d7":0,"d8":0,"d9":0},
 "total":0.0,
 "per_run":[{"id":"9","score":0,"vs_baseline":"明显更好/略好/持平/更差","issues":["…"]}],
 "reasons":{"d1":"…"},
 "fix_proposals":[{"dim":"dX","file":"SKILL.md 或 references/xxx.md","where":"具体段落","change":"具体改法","evidence":"哪条 run 暴露的"}]}
```

总分 = Σ(分 × 权重) / 10。

## 回报（≤150 字）

总分、最弱 2 维、每条 run 的分数。

## 补充说明（全部测试题 × 3 位评审）

1. 结构上，总入口只放路由、安全和全局契约，各维度写法放在维度入口的"## 被总入口调用时：段落契约"一节。结构维度（d1–d7、d9）把总入口、它直接路由到的维度入口（维度表里列出的入口 skill）和参考文件作为一个系统来评；d1 只看总入口的 frontmatter。
2. d7 额外考察可扩展性：新增一个维度是否只需改维度表一行。d6 额外考察可移植性：用到工具的 skill 是否自带 scripts/divine.py，单独拷走能否运行。
3. run 执行记录里的工具命令如果用的是测试机上可用 python 的实际路径，属于测试环境替换，不扣分。
4. 分段格式（REPLY-1 / USER-2 继续 / REPLY-2）按两部分合起来评，续接提示不算问号。
5. 打分标尺：9 分 = 找不出可点名的缺陷；8 分 = 有 1–2 处小缺陷，不影响用户；7 分 = 有影响用户体验或规则执行的缺陷；≤6 = 安全、编造、明显答非所问。每个分数都要能对应到 issues。
6. 你是独立评审，不参考任何其他评审文件。不运行 python 或其他脚本。
